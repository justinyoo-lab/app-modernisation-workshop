# 4. Azure 서비스로 의존성 이전하기

## 목표

이전 실습에서 준비한 Azure 연동 코드와 테스트가 기존 동작을 유지하는지 검토합니다. 필요한 부분을 수정하고 로컬에서 검증합니다.

## 실습 범위

이 실습에서는 [실습 3: JDK 25로 업그레이드하기](03-upgrade.md)에서 준비한 Azure 연동 코드와 테스트를 요구사항과 대조합니다. 빌드와 모의 테스트 결과도 함께 검토합니다. 문제가 있으면 승인한 범위에서 수정하고 로컬 테스트를 다시 실행합니다. 실제 Azure 서비스에 연결할 통합 테스트도 준비하되, 이 단계에서는 실행하지 않습니다.

### Azure 이전 대상과 보존할 동작

| 기존 의존성 | 목표 | 보존할 동작 |
| --- | --- | --- |
| PostgreSQL 컨테이너 | Azure Database for PostgreSQL Flexible Server | DB 연결과 S3 처리 경로(`dev` 프로필 외)의 메타데이터 기록 및 조회 |
| RabbitMQ | Azure Service Bus 큐 | 프로듀서와 컨슈머의 메시지 규약, 처리 결과와 오류 복구 |
| `dev`의 로컬 파일과 `dev` 외 AWS S3 | 비공개 Azure Blob Storage | 업로드 후 조회, 접근 제어와 파일 식별 방식 |

## 실습 전 확인 사항

이전 실습의 JDK 25 빌드와 모의 테스트 결과를 확인한 뒤, 같은 Copilot app 터미널의 **앱 루트**를 계속 사용합니다.

## 코드 이전 요구사항 확인

다음 요구사항이 생성된 코드와 테스트에 반영됐는지 확인합니다.

```text
`.github/modernize/rulebook/`의 지침과 실제 업그레이드 결과를 읽고
Azure 연동 코드와 테스트를 검토해 줘. 파일을 변경하거나 명령을 실행하지 마.
JDK 25와 현재 Spring Boot 버전을 유지하고 web과 worker의 기존 기능을 보존하는지 확인해 줘.

- **PostgreSQL:** Flexible Server와 TLS를 사용하고, 커넥션 풀에서 관리 ID/Entra 인증과 토큰 갱신이 올바르게 동작하는지 확인해 줘.
- **Service Bus:** RabbitMQ를 대체하는 프로듀서와 컨슈머를 확인해 줘. 메시지 형식과 처리 동작을 유지하는지, 성공 시 complete, 실패 시 abandon/dead-letter를 수행하는지 검토해 줘. 같은 메시지를 중복 수신해도 결과가 달라지지 않는지(멱등성), 종료 시 컨슈머를 정리하는지도 확인해 줘. worker는 계속 실행되는 컨슈머로 유지하고 KEDA는 추가하지 마.
- **Blob:** 파일을 비공개 Blob에 저장하고 인증된 서버를 통해 조회하는지 확인해 줘. 컨테이너 로컬 디스크를 영구 저장소로 쓰거나 공개 컨테이너, 무기한 SAS URL을 사용하지 마. `dev` 외 S3 경로의 코드와 설정, DB 메타데이터 기록과 조회 동작을 보존하고, `dev` 업로드 경로에 없던 DB 기록을 추가하지 마.
- **인증과 SDK:** 로컬 개발 자격 증명과 ACA 관리 ID를 구분하고, 선택한 인증 방식(예: `DefaultAzureCredential`의 자격 증명 확인 순서)이 실제로 어떻게 동작하는지 설명해 줘. 비밀정보를 코드, 설정, Git에 넣지 마. 현재 Spring Boot 및 JDK 25와 Azure SDK의 호환성을 근거와 함께 확인하고, 호환되지 않는 Spring Cloud Azure starter는 추가하지 마.
- **문서와 테스트:** 변경된 환경 변수, 필요한 리소스와 역할, DB 초기화 절차가 문서화됐는지 확인해 줘. 단위 테스트는 Azure 없이 실행할 수 있어야 해. DB, 큐, Blob 통합 테스트는 별도로 준비하는 계획을 세워 줘.
- **제외 범위:** S3 데이터 이전이나 AWS 리소스 접근은 필요성만 검토하고 실행하지 마. 인프라 생성, 실제 DB 변경과 데이터 이전, 이미지 게시, 배포는 작업 목록에서 제외해 줘.

각 판단의 근거로 파일 경로와 줄 번호를 제시하고, 코드에서 확인할 수 없는 항목은 미확인으로 표시해 줘.
```

## 생성 결과 검토

- [ ] 위 검토 요청을 Copilot app 채팅에 보냅니다. 앱 코드나 Azure 리소스는 변경하지 않고, 응답에 제시된 파일 경로와 줄 번호를 확인합니다.
- [ ] 앱 루트에서 [실습 3: JDK 25로 업그레이드하기](03-upgrade.md) 이후의 변경을 확인합니다. `git diff`에서 앱 외부 파일, 불필요한 생성물이나 비밀정보가 포함되지 않았는지 살핍니다.

    ```text
    git status --short
    git log --oneline "$before..HEAD"
    git diff "$before"
    ```

- [ ] `infra/`의 Bicep에서 `identity`와 `Microsoft.Authorization/roleAssignments`를 찾습니다. `principalId`가 해당 앱의 관리 ID인지, web에는 Service Bus Data Sender, worker에는 Data Receiver 역할이 할당됐는지 확인합니다. Blob 역할이 해당 컨테이너 범위에만 적용되는지, Contributor나 구독 전체 권한을 부여하지 않았는지도 살핍니다. 근거가 되는 파일 경로와 줄 번호를 기록하고, 확인할 수 없는 역할 할당은 미확인으로 남깁니다.
- [ ] [실습 3: JDK 25로 업그레이드하기](03-upgrade.md)에서 실행한 `./mvnw -pl web,worker -am verify` (PowerShell은 `./mvnw.cmd -pl web,worker -am verify`)의 터미널 결과를 확인해 단위 테스트 상태를 기록합니다. Azure 통합 테스트는 실행하지 않고 미실행으로 표시합니다.
- [ ] 각 앱의 `application*.yml` 또는 `application*.properties`와 README에서 로컬 `dev`와 Azure 설정으로 실행하는 방법을 확인합니다.
- [ ] PostgreSQL 권한과 초기화 절차는 [5. azd 배포 산출물 준비하기](05-prepare-azd.md)에서 검토하고, 실제 초기화는 [6. azd로 ACA에 배포하기](06-deploy-aca.md)에서 승인 후 수행합니다.

## 발견 사항 조치

수정하거나 추가로 확인할 내용이 있으면 같은 Copilot app 채팅에 다음과 같이 요청합니다.

```text
위 검토 결과를 코드 수정이 필요한 항목과 추가로 확인할 항목으로 구분해 줘.
각 항목의 근거, 영향, 수정 방법과 필요한 테스트를 제시해 줘.
실제 Azure 연결이 필요한 검증은 따로 표시해 줘.
파일을 변경하거나 명령을 실행하지 마.
```

코드 수정이 필요하면 제안된 범위를 검토합니다. 승인한 항목을 명시해 별도로 수정을 요청합니다.

```text
위에서 승인한 항목만 수정하고 관련 테스트와 문서를 갱신해 줘.
앱 루트에서 현재 셸에 맞는 `../scripts/`의 `use-java` 도우미로 JDK 25를 선택해 줘.
같은 셸에서 앞서 실행한 빌드와 web/worker 모의 테스트를 실행해 줘.
실제 Azure 연결, 리소스 생성, DB 변경과 배포는 하지 마.
변경 파일, 테스트 결과와 남은 미검증 항목을 보고해 줘.
```

수정 후 변경 내용과 테스트 결과를 살펴봅니다. 파일이나 리소스를 변경하지 않는 검토를 다시 요청해 문제가 해결됐는지 확인합니다.

## Azure 통합 테스트 준비

실제 Azure의 DB, Service Bus와 Blob에 연결해 검증할 테스트와 실행 스크립트를 준비합니다. 이 테스트는 앞서 실행한 모의 테스트와 별개입니다. Copilot app 채팅에 다음을 요청합니다.

```text
현재 앱의 Azure 서비스 코드, 테스트와 빌드 설정을 읽고 실제 Azure 연결용 통합 테스트와 실행 스크립트를 작성해 줘.
기존 테스트 도구를 우선 사용하고 Azure 리소스 생성이나 실제 연결 없이 코드와 실행 안내를 준비해 줘.

- PostgreSQL의 TLS 연결과 테스트 데이터의 기록 및 조회, Blob의 비공개 저장 및 조회, Service Bus의 메시지 송수신과 처리 결과를 각각 검증해 줘.
- 실제 코드의 동작과 테스트 대상에 근거해 성공 조건을 작성해 줘. 확인할 수 없는 동작은 추측하지 말고 미검증으로 표시해 줘.
- 테스트 전용 데이터와 고유 식별자를 사용하고 기존 데이터나 메시지를 수정하거나 삭제하지 마. 메시지는 테스트 전용 큐에서만 수신해 다른 메시지를 소비하지 않도록 해 줘. 자동 정리는 하지 말고 생성한 테스트 데이터와 별도 정리 방법을 안내해 줘.
- Maven의 `azure-it` 프로필로 실제 Azure 연결 테스트를 명시적으로 실행하도록 분리해 줘. 앱 루트에서 `./mvnw -Pazure-it -pl web,worker -am verify`로 실행하고, PowerShell에서는 `./mvnw.cmd`를 사용해 줘.
- 기본 빌드와 모의 테스트에서는 실제 Azure 연결 테스트가 실행되지 않게 해 줘. `azure-it` 실행 시 필수 대상이 없거나 연결에 실패하면 실패로 보고해 줘. 테스트가 없거나 모두 건너뛴 경우도 성공으로 처리하지 마.
- 테스트 대상은 `AZURE_IT_PG_HOST`, `AZURE_IT_PG_DATABASE`, `AZURE_IT_PG_USER`, `AZURE_IT_BLOB_ENDPOINT`, `AZURE_IT_BLOB_CONTAINER`, `AZURE_IT_SERVICEBUS_NAMESPACE`, `AZURE_IT_SERVICEBUS_QUEUE` 환경 변수로 받아 줘. 값이 누락되거나 비어 있거나 `<...>` 형태이면 연결하지 마.
- 로컬 테스트에서는 `AzureCliCredential`로 Azure CLI에 로그인한 계정만 사용하고 다른 자격 증명으로 대체하지 마. PostgreSQL에는 해당 계정의 Entra 토큰과 DB 사용자로 인증하고 TLS로 연결해 줘. 토큰은 메모리에서만 사용하고 출력하거나 저장하지 마.
- 앱 루트에 `scripts/run-azure-it.sh`와 `scripts/run-azure-it.ps1`을 만들어 줘. 이미 같은 파일이 있으면 덮어쓰지 말고 보고해 줘. 두 스크립트는 앱 루트에서 직접 실행하고 현재 셸의 환경을 변경하지 않아야 해.
- `.sh`는 Bash 3.2와 Bash 5에서 실행할 수 있도록 `#!/usr/bin/env bash`와 LF를 사용하고 실행 권한을 부여해 줘. Windows `.ps1`은 UTF-8 BOM과 LF를 유지해 줘. 스크립트 위치를 기준으로 `../../scripts/powershell-bootstrap.ps1`을 불러오고, `Initialize-WorkshopScript`로 Windows PowerShell 5.1에서 PowerShell 7로 실행을 위임해 줘. 설치 승인 옵션은 사용하지 말고 PowerShell 7이 없으면 종료해 줘.
- 스크립트의 실행 환경에서 `../scripts/use-java.sh --jdk 25`를 `source`로 불러오거나 `../scripts/use-java.ps1 -Jdk 25`를 dot-source해 JDK를 선택해 줘. PowerShell에서는 직접 실행해도 환경 변수가 호출자 프로세스에 남지 않도록 변경 전 값을 보존하고 실패 시에도 복원해 줘. `azure-it` 프로필이 테스트와 연결되어 있는지 확인하고 명령 실패나 누락을 명시적으로 보고해 줘.
- `az account show`와 `azd env get-value`로 현재 Azure CLI 사용자, 구독, 리소스 그룹과 테스트 대상 값을 조회해 줘. `AZURE_IT_PG_USER`는 Azure CLI 사용자 이름으로 설정해 줘. 참가자가 이 이름과 DB 사용자 이름이 일치하는지 확인하도록 해 줘. Azure CLI에 로그인한 사용자 계정만 지원하고 다른 계정 유형이면 중단해 줘. azd와 Azure CLI 구독이 다르거나 값이 없으면 중단하고 다른 구독으로 전환하지 마.
- `AZURE_IT_APP_SERVICEBUS_NAMESPACE`와 `AZURE_IT_APP_SERVICEBUS_QUEUE` 출력으로 앱 큐를 확인해 줘. 테스트 큐가 같은 네임스페이스의 앱 큐와 같으면 중단해 줘. 테스트 대상, 앱 큐, 사용자, 구독, 리소스 그룹, 데이터 읽기와 쓰기 범위, 정리 필요성을 표시하되 토큰이나 비밀은 표시하지 마.
- 참가자가 실제 대상, DB 사용자, 권한, 네트워크, 비용과 데이터 변경 범위를 확인하도록 해 줘. 대화형 터미널에서 명시적으로 동의한 경우에만 `azure-it` 테스트를 실행해 줘. CI나 비대화형 환경에서는 자동 승인하지 말고 테스트를 실행하지 않은 채 실패로 종료해 줘.
- 실행할 때마다 새 테스트 결과를 확인해 DB, Blob, Service Bus 테스트가 각각 실행되고 성공했는지 검증해 줘. 테스트 실패, 결과 누락 또는 건너뛰기는 성공으로 처리하지 말고 종료 코드에 반영해 줘. 기존 테스트 결과와 사용자 데이터를 삭제하거나 덮어쓰지 마.
- 스크립트의 성공, 조회 실패, 구독 불일치, 앱 큐와 테스트 큐 충돌, 사용자 거부, 비대화형 실행과 테스트 실패를 가짜 명령으로 검증해 줘. 실제 Azure 연결과 로그인, 리소스 생성, DB 변경, 배포, 설치는 하지 마.
```
